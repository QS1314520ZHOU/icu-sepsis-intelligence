## 已实现的病程快照基础

- 新增 notes 模块：ClinicalNoteSource 是院内适配器的内部契约，明确批次及逐份文书的患者/住院/科室归属；默认没有医院 HTTP 适配器，功能关闭。未从字段名猜测 BLH/BQDM 的映射、HTTP 方法、认证、分页或时间来源，未调用真实生产病历。
- MongoDB 独立集合 sepsis_clinical_note_snapshot、sepsis_clinical_note_sync_state，均在现有 icu_sepsis_* 业务库初始化保护下建立索引。正文及候选原文编号采用 AES-256-GCM 加密，患者、住院、科室、快照ID和版本键绑定到认证附加数据。密钥环仅来自服务端配置，不存数据库；加密密钥和去重指纹密钥分别指定 ID，支持保留旧解密密钥并轮换新写入密钥。
- 以经过验证的上下文、候选标识、类型、正文及时间元数据生成带密钥指纹；重复内容不重复插入，内容变化保存独立版本。标识关系未确认时明确标为候选，不能将内容版本数当作唯一文书数或认定源系统最新版本。源正文及候选编号不进入默认审计。
- 批次或逐份文书的归属不能确认时拒绝纳入；混合住院返回只保留归属明确的文书并标记不完整。来源数量超过本地技术上限、正文缺失/过长、部分拒绝或上游完整性不明时分别保留不完整/未知状态，不宣称全量。
- 文书时间仅使用适配器确认的结构化时间类型。默认时间未知，正文中的日期不会被提取为生成、签署或可用时间。
- 不建立 TTL 索引，不设置自动到期删除。长期保存已落实为数据库持久化，不是进程缓存；确切年限、归档、合法更正/删除、数据库与备份层加密和密钥保管/恢复仍需按院方制度落实，未擅自解释为无限期开放访问。
- 新接口：GET /api/v1/patients/{patientId}/clinical-notes（分页元数据）；GET /{id}（受控解密原文）；POST /sync（医生主动同步）。目录/正文沿用医生、护士、质控权限，每次重新核验当前患者、住院和科室授权；手动同步仅医生可请求。访问审计记录当前操作者和固定用途，不包含病程全文、密钥或接口访问参数。
- 首次读取在启用且已提供适配器时可触发同步；提供独立定时任务契约，不依赖患者是否曾打开页面。仅对适配器确认仍在科的宿主患者集合同步；分批上限下轮转处理，显示分批/失败状态。没有可靠医院变更或出科事件时不宣称事件同步已完成，也不能保证获取了出科前最后一份文书。
- 读取失败、超时、密钥不可用或归属不明均独立降级。已有密文快照保留，来源关闭/不可用后，仍可在当前有效权限和密钥下读取；不能因旧权限曾有效就永久授权。转科后的历史授权流程仍需真实宿主核实，当前保持严格同科室及当前住院约束。
- “记录与依据”页面新增病程记录与长期快照：显示同步状态、完整性、最后成功/完整同步时间、可信文书时间、保存时间、标识关系和历史原文。使用文本渲染，HTML 或指令只作不可信正文展示；没有把病程原文发送模型。
- 此批没有实现或启用病程 AI 综合复核；模型部署位置、院内审批、最小必要片段与保护方式未核实前不发送可识别病历。当前不可信正文显示测试不等于已经通过模型提示注入验证。

## 配置与继续接入条件

默认 CLINICAL_NOTES_SYNC_ENABLED=false。密钥配置为 CLINICAL_NOTES_KEYS_JSON（密钥 ID 到 Base64 256位密钥的 JSON），并分别配置 CLINICAL_NOTES_ACTIVE_KEY_ID、CLINICAL_NOTES_FINGERPRINT_KEY_ID；不要将真实密钥写进仓库。缺失或错误的病程密钥只使病程功能不可用，不阻塞规则引擎。密钥轮换时保留历史解密密钥，同一密钥 ID 不应更换原密钥值，保持去重密钥稳定；移除旧密钥会使对应历史正文无法解密，需纳入院方恢复制度。

技术上限和后台扫描频率可由 CLINICAL_NOTES_MAX_DOCUMENTS、CLINICAL_NOTES_MAX_BODY_CHARACTERS、CLINICAL_NOTES_MAX_SYNC_PATIENTS、CLINICAL_NOTES_SCAN_MS 配置。它们不是医院接口的已确认上限或临床时间口径。尚无实际 HTTP 客户端，因此 HTTP 超时/响应字节上限/编码/严格 JSON/分页与认证仍是医院适配器接入工作，不能将内部契约测试描述为 BLBCJL 已联调。

当前工作区未找到可用于核对的接口样本 记录.txt；未为复制附件的转义问题放宽线上 JSON 解析，也没有写入示例真实访问参数。
